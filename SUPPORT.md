# VELCORA Linux Support

## 1. Welcome

Welcome to VELCORA Linux Support.

VELCORA is a Debian-based Linux operating system focused on Cloud Administration.

This document explains how users, administrators, developers and community members can request assistance.

The goal is to make support organised, accessible and useful.

## 2. Where to Get Help

The official VELCORA GitHub repository should be the primary location for project support.

The following channels should be used for different types of requests.

### GitHub Issues

Use GitHub Issues to report:

- Software bugs.
- Installation problems.
- Boot failures.
- Hardware compatibility problems.
- Network configuration problems.
- Package management issues.
- Documentation errors.
- Reproducible system problems.

Before creating an issue, check whether someone has already reported the same problem.

### GitHub Discussions

Use GitHub Discussions for:

- General questions.
- Technical discussions.
- Configuration advice.
- Feature proposals.
- Community assistance.
- Development discussions.
- Ideas for improving VELCORA.

Discussions should not be used to publish sensitive security vulnerabilities.

### Documentation

Before requesting assistance, users should consult the available VELCORA documentation.

Documentation should include:

- Installation instructions.
- User guides.
- Administrator guides.
- Cloud Administration guides.
- Troubleshooting procedures.
- Security information.
- Development instructions.

## 3. Reporting a Bug

When reporting a bug, provide as much relevant information as possible.

A useful report should include:

1. VELCORA version.
2. Kernel version, if known.
3. Hardware configuration.
4. A description of the problem.
5. Steps to reproduce the problem.
6. Expected behaviour.
7. Actual behaviour.
8. Relevant error messages.
9. Relevant logs or screenshots.

Do not include passwords, private keys, access tokens or personal information in public reports.

## 4. Requesting a Feature

Feature requests should explain:

- What functionality is being requested.
- Why it would be useful.
- Which users would benefit.
- How it relates to Cloud Administration.
- Whether an existing feature already provides similar functionality.

Feature requests are reviewed according to project priorities, technical feasibility, security and available development resources.

Submitting a request does not guarantee implementation.

## 5. Installation Support

Installation-related support requests should include:

- The installation image version.
- Whether the image was verified.
- The hardware or virtual machine used.
- The installation stage where the problem occurred.
- Relevant error messages.
- Any troubleshooting already performed.

Users should avoid sharing sensitive information from their systems.

## 6. Hardware Compatibility

Hardware-related reports should include:

- Device manufacturer.
- Device model.
- Processor information.
- Graphics hardware.
- Network hardware.
- Storage configuration.
- Relevant driver information.

The project may request additional diagnostic information when necessary.

Hardware support should not be assumed unless the relevant device has been tested or appropriately verified.

## 7. Security Problems

Security vulnerabilities must not be submitted as public support issues.

Follow the reporting instructions in SECURITY.md.

If you believe your system has been compromised, avoid sharing sensitive diagnostic information publicly.

## 8. Support Responsibilities

### Users

Users should:

- Provide accurate information.
- Follow documented troubleshooting procedures.
- Avoid publishing sensitive information.
- Treat community members respectfully.
- Provide additional information when requested.

### Contributors

Contributors should:

- Help users where they have relevant knowledge.
- Avoid presenting guesses as confirmed solutions.
- Reference official documentation where possible.
- Report confirmed bugs through the appropriate process.

### Maintainers

Maintainers should:

- Review reported problems.
- Identify reproducible issues.
- Direct users to relevant documentation.
- Prioritise important problems.
- Communicate known limitations.
- Avoid promising fixes without an implementation plan.

## 9. Support Limitations

VELCORA is a developing operating system project.

During early development:

- Some functionality may be incomplete.
- Some hardware may not be supported.
- Documentation may change.
- Development builds may contain bugs.
- Response times may vary.
- Support availability may be limited.

The project does not guarantee immediate responses or fixes.

## 10. Third-Party Software

VELCORA may include software maintained by external developers and projects.

Issues affecting third-party components may need to be reported to their respective upstream maintainers.

The VELCORA team will determine whether a problem originates from VELCORA configuration, system integration or an upstream component.
